# M1 演示与接口

## 5—8 分钟演示顺序

1. 启动后以学生 A 进入「寻找座位」。默认选下一个可预约整点；按教室/区域、插座筛选，选择一个绿色座位并确认。
2. 切换学生 B，选择相同教室和时段，刚才的座位已不可预约。即使直接发同座位同时间的 API 请求，也应返回 409。
3. 切回学生 A，「我的预约」显示待签到与预约编号。
4. 记录预约的开始时间，切换管理员，在「空间管理」推进演示时钟到开始前 15 分钟至开始后 15 分钟之间。顶部显示当前北京时间；按差值填写推进分钟。点击「查看当日签到码」，记住该码。切回学生 A 输入码，状态变为已签到。
5. 若要演示违约，在一个尚未开始的时段另预约一个座位。分别推进到开始前 15 分钟、开始后 10 分钟，每次查看学生站内通知。再推进到开始后 15 分钟，预约变为违约，查询同一座位可见限制已释放。到达 15 分钟整不再允许签到。一次跳过提醒窗口只产生违约通知，不补发过期提醒。
6. 切换管理员到「跨模块联调」，先在「寻找座位」选择未来时段；为同一个无个人预约的教室，添加 `M2 / approval-001` 和 `M3 / repair-001` 两条限制（编号需手动填写）。查看座位不可预约，悬停可看状态来源。
7. 在联调页只解除 M3，座位仍受 M2 限制；再解除 M2，座位恢复。已解除的业务编号为终态，不用同编号重新启用，新的业务使用新编号。
8. 演示教室开放时间修改、停用座位、管理员统计。重启后预约数据保留，时间偏移恢复真实时间。

## 数据模型

- `rooms`：教室、区域、开放小时、启用状态。
- `seats`：教室外键、教室内唯一编号、插座、启用状态。
- `reservations`：用户、座位、开始/结束、状态、创建时间。
- `restrictions`：来源 M2/M3、来源业务编号（联合唯一）、教室、有效区间、是否解除。
- `messages`：用户、预约、通知类型、正文；预约+类型唯一，避免重复通知。

区间为半开 `[start,end)`，相邻预约不冲突。有效可用性由停用状态、开放时间、M1 有效预约、M2/M3 未解除且时间重叠的限制共同计算。写操作通过 SQLite `BEGIN IMMEDIATE` 串行化，查询检查与插入属于同一事务。提醒和违约写入同样事务化。

## 接口契约

完整请求模型与错误响应可在运行中的 `/docs` 查看。请求头为 `X-Demo-User: student-a | student-b | admin`，**仅演示适配，正式版由公共认证提供身份**。缺少管理员身份/无效身份返回 401，学生访问管理接口返回 403。下述时间均为北京时间 ISO 8601，例如 `2026-10-22T09:00:00`。

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/meta` | 服务器演示时间与空间列表 |
| GET | `/api/seats?start=...&end=...&room_id=1&outlet=true` | 时段状态与来源 |
| POST | `/api/reservations` | `{seat_id,start,end}` 创建预约，201 返回编号 |
| GET | `/api/reservations` | 当前身份的预约历史 |
| POST | `/api/reservations/{id}/cancel` | 只可取消自己的待签到预约 |
| POST | `/api/reservations/{id}/checkin` | `{code}` 动态码签到 |
| GET | `/api/messages` | 当前身份站内通知 |
| GET | `/api/admin/overview` | 汇总、按空间统计、座位与外部限制 |
| GET | `/api/admin/rooms/{id}/code` | 管理员获取当日签到码 |
| POST / PUT | `/api/admin/rooms` / `/api/admin/rooms/{id}` | `{name,area,opens,closes,active}` |
| POST / PUT | `/api/admin/seats` / `/api/admin/seats/{id}` | `{room_id,label,outlet,active}` |
| POST | `/api/integrations/restrictions` | 添加 M2/M3 限制 |
| DELETE | `/api/integrations/restrictions/{source}/{external_id}` | 幂等解除指定来源 |
| POST | `/api/demo/advance` | 管理员演示专用，`{minutes:15}` |

队友通过 HTTP 调用示例（日期改为未来的演示日期）：

```sh
curl -X POST http://127.0.0.1:8000/api/integrations/restrictions \
  -H 'Content-Type: application/json' -H 'X-Demo-User: admin' \
  -d '{"source":"M2","external_id":"approval-001","room_id":2,"start":"2026-10-22T09:00:00","end":"2026-10-22T11:00:00"}'
curl -X DELETE http://127.0.0.1:8000/api/integrations/restrictions/M2/approval-001 \
  -H 'X-Demo-User: admin'
```

重复创建相同来源编号与相同参数返回既有记录；相同编号不同参数返回 409。释放只影响该条记录，重复释放返回成功。已有个人预约则创建限制返回 409；M2/M3 可彼此叠加。不存在教室/座位返回 404，输入业务规则无效返回 422，冲突返回 409，错误正文为 `{"detail":"原因"}`。调用方必须检查状态码后再标记同步成功。

## 三人接入顺序

A 保留 M1 业务与测试；B 将数据模型迁入统一 Alembic/PostgreSQL、接入真实 M2 HTTP 调用和部署；C 提供用户身份/RBAC/通知接口，M3 通过相同契约写入维修限制。最终三人联合测试真实审批与维修流程，本页模拟请求不能代替联合验收。
