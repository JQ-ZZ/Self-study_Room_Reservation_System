## 1. 范围

M2 负责「整间教室」的预约申请与两级审批，审批通过后占用该教室在指定时段内的全部座位。
个人座位预约属于 M1；维修下架属于 M3。M2 不直接操作其他模块数据库，只通过公开 HTTP 接口交互。

不在本期范围：

- 教室主数据的增删改（由 M1 提供只读查询）
- 座位级预约（M2 只按整教室处理）
- 通知的具体投递（复用 C 的公共通知服务）
- 审批之外的资源计费、门禁联动

## 2. 角色与权限

| 角色 | 能做什么 | M2 接口校验 |
|---|---|---|
| 学生 / 教师（申请人） | 提交申请、查看自己的申请、撤销符合条件的申请 | `student` / `teacher` |
| 一级审批人 | 处理待一级审批的申请（通过/驳回） | `approver_l1` |
| 二级审批人 | 处理待二级审批的申请（通过/驳回） | `approver_l2` |
| 管理员 | 查看全部、代审批、运维重试 | `admin` |

规则：

1. 没有对应角色时接口返回 403（不能只靠前端隐藏按钮）。
2. 同一审批人不能同时完成一级和二级审批（四眼原则）。
3. 申请人只能撤销自己的申请；管理员可代为撤销。

## 3. 业务规则

### 3.1 提交（M2-01）

- 必填：教室、开始时间、结束时间、用途。
- 开始时间必须晚于当前时间；结束时间必须晚于开始时间。
- 单次申请最长 12 小时（`M2_MAX_APPLICATION_HOURS`，可配置）。
- 教室必须存在于 M1；M1 不可达时返回 503，而不是静默放行。
- 提交时若该教室时段已被**已批准**的申请占用，返回 409。
- 提交后状态为 `PENDING_L1`，写入 `expires_at = now + 审批时限`。

### 3.2 两级审批（M2-03）

- 一级通过 → `PENDING_L2`；二级通过 → `APPROVED`。
- 任意一级驳回 → `REJECTED`，记录驳回人和原因。
- 审批意见可选，但记录进审批轨迹。
- 二级审批通过前再次检查冲突；冲突则返回 409，状态保持不变，审批人可等待对方撤销或驳回本申请。
- 审批通过时，与 Outbox 记录同事务写入，保证「审批结果」和「待同步任务」不丢。

### 3.3 超时撤销（M2-05）

- 待审批超过时限（演示 90 秒，生产建议 24 小时，`M2_APPROVAL_TIMEOUT_SECONDS`）自动置为 `EXPIRED`。
- 由后端定时任务执行，不依赖用户刷新页面。
- 审批轨迹写入系统记录（`approver_id=system`）。
- 已经是 `APPROVED` 的申请不参与超时撤销。

### 3.4 查询与取消（M2-06）

- 申请人可查看自己的全部申请及审批轨迹。
- 审批人可查看待办列表和申请详情。
- 待审批状态（`PENDING_L1` / `PENDING_L2`）可由申请人撤销。
- 已批准且**尚未开始**的申请可撤销；撤销会写回 `RELEASE` 释放教室占用。
- 已开始或已结束的申请不可撤销（本期不做提前结束）。
- 已驳回 / 已撤销 / 已超时的申请不可再次流转。

### 3.5 M2 → M1 状态写回（M2-07）

- 二级审批通过：调用 M1 占用接口，占用该教室指定时段的**全部座位**。
- 驳回、审批中超时撤销：未产生占用，无需写回。
- 已批准后撤销：调用 M1 释放接口。
- 调用失败：
  - M2 申请状态保持真实业务结果（已批准），**不得显示“占用成功”**；
  - `sync_records` 记录 `FAILED / DEAD`、错误信息、重试次数；
  - 后台退避重试，管理员可在运维台手动重试；
  - 页面同时展示「审批状态」和「同步状态」。
- 幂等键：`application_id`。M1 必须保证重复占用 / 重复释放幂等。

## 4. 状态机

```text
                    ┌──────────────┐
   提交 ───────────▶│ PENDING_L1   │
                    └──────┬───────┘
             一级通过 │      │ 一级驳回 / 撤销 / 超时
                    ▼      ▼
                    ┌──────────────┐        ┌──────────┐
                    │ PENDING_L2   │───────▶│ REJECTED │
                    └──────┬───────┘        └──────────┘
             二级通过 │      │ 二级驳回 / 撤销 / 超时
                    ▼      ▼
                    ┌──────────────┐        ┌───────────┐
                    │  APPROVED    │───────▶│ CANCELLED │
                    └──────────────┘ 开始前撤销（释放占用）
```

允许的流转在代码中集中定义于 `app/state_machine.py`，非法流转返回 409。

## 5. 数据模型

### applications

| 字段 | 类型 | 说明 |
|---|---|---|
| id | varchar(36) PK | UUID |
| room_id / room_name | varchar | 教室标识与快照名称 |
| applicant_id / applicant_name | varchar | 申请人 |
| purpose | varchar(255) | 用途 |
| start_time / end_time | timestamp (UTC) | 使用时段 |
| status | varchar(20) | 状态机状态 |
| reject_reason | varchar(255) | 驳回/撤销/超时说明 |
| created_at / updated_at | timestamp | 时间戳 |
| expires_at | timestamp | 审批截止时间 |
| decided_at | timestamp | 终态时间 |

索引：`(room_id, start_time, end_time)`、`(status, expires_at)`、`applicant_id`。

### approval_records

审批轨迹，追加写，不修改历史。字段：`application_id`、`level`（1/2/0）、`approver_id/name`、`action`（SUBMIT/APPROVE/REJECT/CANCEL/EXPIRE）、`comment`、`created_at`。

### sync_records（Outbox）

| 字段 | 说明 |
|---|---|
| application_id + action | `OCCUPY` / `RELEASE`，唯一约束 |
| status | PENDING / SUCCEEDED / FAILED / DEAD / SKIPPED |
| attempts | 已尝试次数 |
| last_error | 最近一次错误（截断 500 字符） |
| next_retry_at | 下次重试时间 |

### room_locks

按 `room_id` 建一行，二级审批通过前 `SELECT … FOR UPDATE`，串行化同一教室的并发审批。

## 6. API 一览

前缀：`/api/v1`，认证：`Authorization: Bearer <JWT>`。

| 方法 | 路径 | 角色 | 说明 |
|---|---|---|---|
| POST | `/auth/login` | 公开 | 演示登录（正式由 C 提供） |
| GET | `/rooms` | 登录 | 经 M1 读取教室主数据 |
| POST | `/applications` | 申请人 | 提交申请 |
| GET | `/applications/mine` | 登录 | 我的申请 |
| GET | `/applications/pending` | 审批人/管理员 | 待办列表（按角色过滤层级） |
| GET | `/applications/{id}` | 申请人/审批人/管理员 | 申请详情（含同步状态） |
| GET | `/applications/{id}/approvals` | 同上 | 审批轨迹 |
| POST | `/applications/{id}/approve` | 对应层级审批人 | 通过（二级时做冲突检查） |
| POST | `/applications/{id}/reject` | 对应层级审批人 | 驳回 |
| POST | `/applications/{id}/cancel` | 申请人/管理员 | 撤销（已批准时写回释放） |
| GET | `/sync` | 管理员/申请人 | 同步记录 |
| POST | `/sync/{id}/retry` | 管理员 | 人工重试 |
| POST | `/ops/run-sweep` | 管理员 | 手动执行超时扫描 + 重试 |
| POST | `/ops/m1-failure` | 管理员 | 演示故障注入 |
| GET | `/ops/m1-state` | 管理员 | M1 占用与调用日志 |
| GET | `/health`、`/version` | 公开 | 健康检查、版本 |

成功/失败约定：

- 409：状态不允许、时段冲突；响应 `detail` 为字符串或 `{message, conflicting_application_id}`。
- 403：角色不足。
- 422：参数校验失败。
- 503：M1 不可达（仅提交时校验教室、管理接口代理）。

## 8. 待确认问题（组内评审）

1. **角色命名**：`approver_l1` / `approver_l2` 是否与 C 的 RBAC 方案一致？是否需要按教室类型配置审批人？
2. **提交期冲突**：目前允许重叠申请进入审批，由二级审批裁决；是否改为提交时直接拒绝？
3. **审批时限**：生产使用 24 小时还是按「距开始时间」动态计算？
4. **撤销规则**：已批准后是否允许撤销？是否需要扣信用分或审批人同意？
5. **M1 接口**：占用接口是否按整教室实现？`application_id` 作为幂等键是否可以？M1 是否需要返回座位级明细？
6. **通知**：审批通过/驳回/超时的站内信由 M2 调用 C，还是 C 订阅事件？
7. **同步失败语义**：当 M1 持续不可用超过最大重试次数，是否需要回滚审批结果？当前选择保留审批结果并人工处理。
8. **部署环境**：测试/生产服务器归属、GitHub Environment 审批人、是否使用 GHCR。
