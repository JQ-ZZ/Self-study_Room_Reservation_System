# AGENTS.md · AI 协作规则（草案）

本文件与代码一起版本管理。AI 助手每次任务前先读本文件，不需要人工重复交代背景。

## 1. 项目边界

- 业务模块：M1 自习座位预约、M2 整教室预约审批、M3 物业报修工单。
- 公共层 D：认证/RBAC、通知、审计、公共页面，由成员 C 负责。
- AI 不得自行增加业务模块、替换技术栈或引入 Kubernetes、消息队列等基础设施。

## 2. 目录与所有权

| 路径 | 负责人 |
|---|---|
| `backend/services/m1/**` | A |
| `backend/services/m2/**` | B |
| `backend/services/m3/**` | C |
| `backend/shared/**`、`frontend/` 公共部分 | C |
| `deploy/**`、`.github/**`、迁移规范 | B |

AI 可以读取全仓，但修改他人模块必须由对应负责人 review。

## 3. 代码规范

- Python 3.12，FastAPI + SQLAlchemy 2.0，类型注解必须完整。
- 统一 `ruff` 检查通过；函数职责单一，错误返回明确的 HTTP 状态码。
- 禁止把业务规则写在前端；后端接口必须独立校验权限。
- 禁止提交密钥、真实密码、`.env` 文件。
- 时间统一 UTC，接口使用 ISO 8601。

## 4. 数据库

- 所有 schema 变更必须通过 Alembic 迁移提交。
- 禁止手工改库，禁止用 `create_all()` 代替迁移（本地 SQLite 快速演示除外）。
- 新增迁移后必须验证：空库 `upgrade head` 成功、`alembic check` 无漂移。
- 迁移只前进；删除列/表至少晚一个发布版本。
- seed 数据脚本化、幂等，与业务逻辑分离。

## 5. 测试要求

- 每个需求编号至少一个测试，断言业务结果和数据库/外部调用副作用。
- 禁止只有「返回 200」的测试；禁止用 mock 绕过需要验证的数据库或 HTTP 行为。
- 跨模块写回必须有失败路径测试（超时、503、重试）。
- 新功能 PR 必须附测试命令与结果。
- 关键测试要经过一次「故意破坏实现」验证，确认测试会失败。

## 6. Git 与评审

- 分支：`feat/<module>-<requirement>`、`fix/...`、`chore/...`；禁止直接 push main。
- PR 标题包含需求编号，例如 `[M2-04] 二级审批冲突检查`。
- 跨模块契约、公共层、schema 变更需要 2 人 review。
- AI 生成的变更必须人工验收后提交；不得由 AI 自动合并冲突或自动 approve。
- 提交信息使用 Conventional Commits。

## 7. AI 使用证据

- 每个功能保留：任务说明、约束、验收标准、AI 产出、人工修改与验收记录。
- 不要求保存全部对话，但关键决策应落到 `docs/adr/` 或 PR 描述中。

## 8. 禁止事项

- 不伪造测试结果、提交记录或部署记录。
- 不在 M1 不可用时让 M2 误报同步成功。
- 不直接访问其他模块的数据库。
- 不自动解决 Git 冲突、不自动合并 PR。
